# Ссылки, которые читает `sing-box tools decode-link`

Справка к команде `sing-box tools decode-link` из podkop-engine (с r13; шифрование VLESS — с r14): какие ссылки она
принимает, какой ключ ссылки в какую опцию outbound превращается и как записать значение.
Общее описание команды — в [README](../README.md), раздел «Ссылка в outbound».

Каждая строка таблиц проверена запуском: пример из строки подан команде на сборках обеих
линий (1.13.21 и 1.14.2), и команда дала названную опцию, предупреждение или отказ.

## Как пользоваться командой

```sh
sing-box tools decode-link 'vless://…'          # ссылка аргументом
echo "$link" | sing-box tools decode-link       # или через stdin: ссылка не попадает в список процессов
sing-box tools decode-link --compact 'vless://…' # outbound одной строкой
```

| Итог | Статус | Что напечатано |
|---|---|---|
| Ссылка принята | 0 | В stdout — outbound в JSON, готовый для `outbounds` в config.json. В stderr — строки `warning: …`, если есть что сказать. |
| Ссылка не годится (в том числе пустой ввод или две ссылки сразу) | 2 | В stderr одна строка `error: …`. В stdout ничего. |
| Прочее (ошибка чтения ввода, неизвестный флаг) | 1 | В stderr строка `error: …`. В stdout ничего. |

Что важно знать о результате:

- Готовый outbound команда собирает самим sing-box, как это делает `sing-box check`, и
  печатает, только если он собрался. Напечатано — значит, этот sing-box его принимает.
  Поэтому часть отказов приходит не от разбора ссылки, а от sing-box: в таблицах про них
  сказано «sing-box такой outbound не собирает».
- Предупреждение значит: outbound создан и соединяется, но что-то из ссылки не перенесено.
  Отказ значит: outbound из такой ссылки в sing-box не заработал бы.
- Сообщения не повторяют ссылку: она секрет, а сообщения оседают в журналах. Значение из
  ссылки попадает в сообщение, только если это простое слово не длиннее 24 знаков. Поэтому в
  таблицах сообщения приведены частями, без значений.
- Сеть команде не нужна: она ничего не открывает и никуда не соединяется.

## Схемы и сборки

| Схема ссылки | Outbound | podkop-engine | podkop-engine-full |
|---|---|---|---|
| `vless://` | vless | да | да |
| `trojan://` | trojan | да | да |
| `ss://` | shadowsocks | да | да |
| `socks://`, `socks4://`, `socks4a://`, `socks5://`, `socks5h://` | socks | да | да |
| `hysteria2://`, `hy2://` | hysteria2 | да | да |
| `tuic://` | tuic | да | да |
| `vmess://` | vmess | нет | да |
| `http://`, `https://` | http | нет | да |
| `hysteria://` | hysteria | нет | да |
| `anytls://` | anytls | нет | да |
| `naive+https://`, `naive+quic://` | naive | нет | да, где собран NaiveProxy |

В обычной сборке ссылка на протокол, которого в ней нет, разбирается, и команда отвечает:
`error: <тип> outbound is not included in this build (podkop_slim), install podkop-engine-full …`,
статус 2. Для `tor://`, `ssh://`, `shadowtls://` и `snell://` ссылок не существует: такие
outbound задаются в конфигурации.

## Общие правила чтения

- Имя схемы и имена параметров читаются без учёта регистра (`allowInsecure` и
  `allowinsecure` — одно и то же). Приставка `amp;` у имени отбрасывается: так выглядит
  ссылка, скопированная из HTML.
- Из повторённых параметров берётся первый. `+` в значении — пробел (так кодируют 3x-ui и
  Marzban); настоящий плюс пишется как `%2B`. Испорченное `%XX` — отказ.
- Параметр, которого команда не знает, даёт предупреждение `<имя> is not supported and is
  ignored` и ни на что не влияет. Параметры TLS в ссылке без TLS и параметры чужого
  транспорта отбрасываются молча: генераторы пишут их всегда.
- Параметр, имя которого — не имя (в нём есть что-то кроме латинских букв, цифр, `-`, `_`
  и `.`), отбрасывается с предупреждением, и его имя в сообщении не повторяется.
- Пробелы по краям ссылки и метка BOM перед ней убираются. Две ссылки в одной строке — отказ.
- Список из одного значения sing-box печатает строкой (`"alpn": "h2"`), из нескольких —
  массивом.
- Где общепринятого параметра нет, опцию задаёт её путь: `sb.<путь>=<значение>` (см. раздел
  ниже). Где генераторы расходятся, решает поведение клиента Xray.

## Как читать таблицы

- **Ключ URL** — имя параметра ссылки; несколько имён в ячейке — синонимы или параметры,
  которые читаются вместе. `<user>`, `<host>`, `<port>`, `#name` — части самой ссылки.
- **Параметр config.json** — путь опции outbound через точки (`tls.utls.fingerprint`).
  Прочерк — опция не пишется.
- **Значения и пример** — как записать значение и что из этого выйдет. Без пометки в начале
  значение записывается в опцию. «Предупреждение» — outbound создан, в stderr строка
  `warning:`. «Отказ» — строка `error:` и статус 2. «Не читается» — параметр молча
  отброшен. В примере показана часть ссылки, которой строка проверялась; для полей JSON —
  сам JSON, который в ссылке закодирован.

## Линии 1.13 и 1.14

Разбор ссылок на обеих линиях один и тот же; различается набор опций sing-box. Только в
1.14 есть: обфускация `gecko` у hysteria2 (`obfs.min_packet_size`, `obfs.max_packet_size`),
`hop_interval_max`, `bbr_profile`, `disable_chrome_parrot`, `realm`, опции QUIC
(`idle_timeout`, `keep_alive_period` и другие) у hysteria, hysteria2 и tuic, `tls.engine`,
`tls.handshake_timeout`. На 1.13 путь `sb.` к любой из них — отказ `sb-unknown`.

Полный список опций каждого outbound с тем, чем каждая задаётся (параметром ссылки, путём
`sb.` или ничем, потому что запрещена), лежит в исходниках рядом с разборщиком:
`common/sharelink/testdata/options-1.13.txt` и `options-1.14.txt`. Тест сверяет его с
опциями sing-box при каждой сборке: новая опция не может появиться незамеченной.


## Адрес: vless, trojan, vmess

Ссылки вида `схема://пользователь@узел:порт?параметры#имя`. У vmess так читается URL-форма; JSON-форма описана ниже.

Схемы, если в строке не сказано иное: `trojan`, `vless`, `vmess`.

| Ключ URL | Параметр config.json | Значения и пример |
|---|---|---|
| `<user>`<br>vless, vmess | `uuid` | UUID пользователя в обычной записи: 32 шестнадцатеричные цифры с дефисами. %XX раскрывается.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443`<br>В outbound: `uuid: "6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11"`<br>Идентификатор пользователя на сервере: всё, что стоит до последнего «@». У vmess — в URL-форме ссылки; в JSON-форме это поле id. |
| `<user>`<br>vless, vmess | `uuid` | UUID без дефисов или заглавными буквами приводится к обычному виду: строчные буквы, дефисы на местах. Дефис перед каждой группой цифр необязателен.<br>Пример: `vless://6F1C9A0E3B524C1E9A552D4A1B0F7C11@example.org:443`<br>В outbound: `uuid: "6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11"`<br>Так UUID читает Xray. sing-box понимает шестнадцатеричный UUID только в обычной записи, поэтому в outbound пишется она. |
| `<user>`<br>vless, vmess | `uuid` | Строка не длиннее 30 байт записывается как есть.<br>Пример: `vless://my-user@example.org:443`<br>В outbound: `uuid: "my-user"`<br>У Xray такая строка заменяет UUID: он вычисляется из неё. sing-box получает из той же строки тот же UUID. |
| `<user>`<br>vless, vmess | — | **Отказ.** 31 байт, больше 36 байт, либо 32–36 байт, которые не читаются как UUID: не шестнадцатеричные цифры, лишний дефис, не хватает цифры.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c1@example.org:443`<br>Сообщение: `the user of the link is not a UUID`<br>В примере у UUID потеряна последняя цифра. Сам UUID в сообщении не повторяется: ссылка — секрет, а сообщения попадают в журналы. |
| `<user>`<br>`<password>` | — | **Отказ.** Перед адресом нет части «…@» или она пуста.<br>Пример: `vless://example.org:443`<br>Сообщение: `missing user in the link`<br>Для vless и vmess это UUID, для trojan — пароль. |
| `<password>`<br>trojan | `password` | Пароль: всё, что стоит до последнего «@». %XX раскрывается.<br>Пример: `trojan://password@example.org:443`<br>В outbound: `password: "password"`<br>Пароль пользователя Trojan. |
| `<password>`<br>trojan | `password` | Особые знаки пишутся как %XX. «/», «+», «=» и даже «@» внутри пароля читаются и без кодирования; «#» и «?» кодировать обязательно: по ним от ссылки отрезаются имя и параметры.<br>Пример: `trojan://pass%3Aw%40rd@example.org:443`<br>В outbound: `password: "pass:w@rd"`<br>Пароль Trojan часто бывает base64 со знаками «/» и «=», и генераторы не всегда его кодируют — поэтому паролем считается всё до последнего «@». |
| `<host>` | `server` | Доменное имя, IPv4 или IPv6 в квадратных скобках (скобки снимаются).<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@192.0.2.1:443`<br>В outbound: `server: "192.0.2.1"`<br>Адрес сервера. IPv6 без скобок не читается: первое же двоеточие считается началом порта. |
| `<host>` | — | **Отказ.** Адрес пуст или у IPv6 не закрыта скобка.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@:443`<br>Сообщение: `invalid server address`<br>Без адреса сервера outbound собрать не из чего. |
| `<port>` | `server_port` | Число от 1 до 65535. Обязателен: порта по умолчанию у этих ссылок нет.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:8443`<br>В outbound: `server_port: 8443`<br>Порт сервера. Всё, что стоит после порта до «?» (например «/» в «…:443/?type=ws»), отбрасывается. |
| `<port>` | — | **Отказ.** Порта нет.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org`<br>Сообщение: `missing server port`<br>У vless, trojan и vmess порт не подставляется: ссылка без него не читается. |
| `<port>` | — | **Отказ.** Не число, 0 или больше 65535.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:70000`<br>Сообщение: `invalid server port`<br>Этим же сообщением кончается ссылка с IPv6 без квадратных скобок. |
| `#name` | `tag` | Текст после «#». %XX раскрывается (если кодирование испорчено, имя берётся как написано), пробелы по краям убираются. Без имени tag не пишется.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443#My%20server`<br>В outbound: `tag: "My server"`<br>Имя сервера, каким его показывает клиент. В JSON-форме vmess имя берётся из поля ps, а «#…» после base64 не читается. |
| `<user>`<br>`<host>`<br>`<port>` | — | **Отказ.** Пробел, табуляция, перевод строки или «://» в части ссылки до «?».<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443 vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:8443`<br>Сообщение: `the address of the link contains a space or another link`<br>Так ловятся две ссылки в одной строке: иначе первая стала бы «пользователем» второй. Вторая ссылка внутри значения параметра даёт отказ «contains a space and another link». |
| `<имя параметра>` | — | **Предупреждение.** Имя параметра — не имя: в нём есть что-то кроме латинских букв, цифр, «-», «_» и «.», либо оно длиннее 128 знаков.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?security=tls&bad%20name=1`<br>Сообщение: `a link parameter whose name is not a name is ignored`<br>В outbound: `tls.enabled: true`<br>Параметр отбрасывается, и его имя в сообщении не повторяется: на месте имени может оказаться что угодно, в том числе часть другой ссылки с её пользователем. Правило общее для всех схем с параметрами. |

## VLESS

Схемы, если в строке не сказано иное: `vless`.

| Ключ URL | Параметр config.json | Значения и пример |
|---|---|---|
| `encryption` | — | **Не читается.** none или пусто: ничего не пишется.<br>Пример: `?encryption=none`<br>Обычное значение в ссылках VLESS. |
| `encryption` | `encryption` | Значение, которое начинается с mlkem768x25519plus: настройка шифрования VLESS (VLESS Encryption) клиента Xray, записывается как есть (с r14).<br>Пример: `?encryption=mlkem768x25519plus.native.0rtt.YBZ6SAP7KfiD5YJiyAGvD49eNYW-f-7IlhMarfyy4k0`<br>В outbound: `encryption: "mlkem768x25519plus.native.0rtt.YBZ6SAP7KfiD5YJiyAGvD49eNYW-f-7IlhMarfyy4k0"`<br>Шифрование VLESS — отдельный слой под VLESS: сервер, у которого оно задано, клиента без него не принимает. Вид настройки: mlkem768x25519plus.<native\|xorpub\|random>.<1rtt\|0rtt>, дальше необязательное дополнение и ключи по 32 или 1184 байта в base64url. До r14 такая ссылка отклонялась. |
| `encryption` | — | **Отказ.** Начинается с mlkem768x25519plus, но такую настройку не принимает и Xray: неизвестный режим, не 1rtt и не 0rtt, неверное дополнение, ключ не в 32 и не в 1184 байта.<br>Пример: `?encryption=mlkem768x25519plus.native.2rtt.YBZ6SAP7KfiD5YJiyAGvD49eNYW-f-7IlhMarfyy4k0`<br>Сообщение: `invalid VLESS encryption`<br>Настройка проверяется тем же разбором, что при запуске sing-box. |
| `encryption` | — | **Предупреждение.** Любое другое значение читается как none.<br>Пример: `?encryption=aes-128-gcm`<br>Сообщение: `encryption has a value that is not VLESS encryption`<br>Такое значение не может означать шифрование VLESS (сам Xray подобную настройку отвергает), поэтому ссылка принимается. |
| `flow` | `flow` | xtls-rprx-vision записывается как есть. Нужны TLS или REALITY и обычный TCP без транспорта либо шифрование VLESS (параметр encryption). Пусто — опция не пишется.<br>Пример: `?security=tls&flow=xtls-rprx-vision`<br>В outbound: `flow: "xtls-rprx-vision"`<br>Режим Vision протокола VLESS. Значение сравнивается буква в букву, с учётом регистра. |
| `flow`<br>`encryption` | `flow` | xtls-rprx-vision вместе с шифрованием VLESS записывается при любом транспорте и без TLS (с r14).<br>Пример: `?encryption=mlkem768x25519plus.native.0rtt.YBZ6SAP7KfiD5YJiyAGvD49eNYW-f-7IlhMarfyy4k0&flow=xtls-rprx-vision&security=tls&type=xhttp&path=%2Fx`<br>В outbound: `flow: "xtls-rprx-vision", encryption: "mlkem768x25519plus.native.0rtt.YBZ6SAP7KfiD5YJiyAGvD49eNYW-f-7IlhMarfyy4k0", transport.type: "xhttp"`<br>С шифрованием VLESS режим Vision работает на его слое, как в Xray; сервер Xray принимает flow поверх XHTTP только так. |
| `flow` | `flow` | xtls-rprx-vision-udp443 записывается как xtls-rprx-vision.<br>Пример: `?security=tls&flow=xtls-rprx-vision-udp443`<br>В outbound: `flow: "xtls-rprx-vision"`<br>Тот же режим, в котором Xray ещё и пропускает UDP на порт 443; sing-box этот порт никак не выделяет. |
| `flow` | — | **Отказ.** Любое другое значение.<br>Пример: `?security=tls&flow=xtls-rprx-direct`<br>Сообщение: `unsupported flow`<br>Других режимов в sing-box нет, а старые (xtls-rprx-direct, xtls-rprx-origin) убраны и из Xray. |
| `flow`<br>`type` | — | **Отказ.** flow вместе с любым транспортом: ws, grpc, http, httpupgrade, xhttp, quic — когда в ссылке нет шифрования VLESS (параметр encryption).<br>Пример: `?security=tls&type=ws&flow=xtls-rprx-vision`<br>Сообщение: `is not supported over the`<br>Vision работает на самом TLS-соединении. Через ws, grpc и http sing-box сам обрывает каждое соединение, через httpupgrade и xhttp отказывает сервер Xray. |
| `flow`<br>`security` | — | **Отказ.** flow в ссылке без TLS и без REALITY — и без шифрования VLESS (параметр encryption).<br>Пример: `?flow=xtls-rprx-vision`<br>Сообщение: `needs TLS or REALITY`<br>Vision работает на TLS-соединении; без TLS или REALITY его нет. |
| `packetEncoding`<br>`packet-encoding`<br>vless, vmess | `packet_encoding` | xudp или packetaddr записывается как есть. Без параметра опция не пишется.<br>Пример: `?packetEncoding=xudp`<br>В outbound: `packet_encoding: "xudp"`<br>Способ упаковки UDP-пакетов. Когда опции нет, sing-box для VLESS сам берёт xudp, для VMess — никакой. У vmess параметр есть только в URL-форме. |
| `packetEncoding`<br>`packet-encoding`<br>vless, vmess | `packet_encoding` | packet записывается как packetaddr.<br>Пример: `?packetEncoding=packet`<br>В outbound: `packet_encoding: "packetaddr"`<br>Именем packet режим packetaddr называют NekoBox и mihomo. |
| `packetEncoding`<br>`packet-encoding`<br>vless, vmess | `packet_encoding` | none: для vless пишется пустая строка — упаковка выключена явно; для vmess опция не пишется.<br>Пример: `?packetEncoding=none`<br>В outbound: `packet_encoding: ""`<br>Без пустой строки sing-box включил бы для VLESS xudp. |
| `packetEncoding`<br>`packet-encoding`<br>vless, vmess | — | **Отказ.** Любое другое значение декодер записывает как есть, и sing-box такой outbound не собирает.<br>Пример: `?packetEncoding=udp`<br>Сообщение: `unknown packet encoding`<br>Отказывает уже сам sing-box: команда собирает готовый outbound так же, как sing-box check. |

## Trojan

Схемы, если в строке не сказано иное: `trojan`.

| Ключ URL | Параметр config.json | Значения и пример |
|---|---|---|
| `security` | `tls.enabled` | Параметра нет — то же, что security=tls: TLS включён. security=none выключает TLS (блок tls не пишется), security=reality включает REALITY.<br>Пример: `trojan://password@example.org:443`<br>В outbound: `tls.enabled: true, tls.utls.fingerprint: "chrome"`<br>У Trojan TLS подразумевается, поэтому ссылки обычно не пишут security. | `flow` | — | **Предупреждение.** Любое непустое значение.<br>Пример: `?flow=xtls-rprx-vision`<br>Сообщение: `flow is not a setting of Trojan and is ignored`<br>flow — настройка VLESS, у Trojan её нет. |

## VMess

JSON-форма v2rayN: `vmess://` и base64 от JSON с полями ниже. В примерах показан сам JSON; в ссылке он закодирован. URL-форма `vmess://uuid@узел:порт?параметры` читает те же параметры TLS, REALITY и транспорта, что vless.

Схемы, если в строке не сказано иное: `vmess`.

| Ключ URL | Параметр config.json | Значения и пример |
|---|---|---|
| `add` | `server` | Адрес сервера: имя или IP. Квадратные скобки вокруг IPv6 (так пишет Marzban) снимаются. Outbound vmess есть только в сборке podkop-engine-full. |
| `add` | — | **Отказ.** Поля нет или оно пусто.<br>Пример: `{"port":"443","id":"6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11"}`<br>Сообщение: `invalid server address`<br>Без адреса сервера ссылка не читается. |

## TLS

Параметры TLS общие для vless, trojan и vmess; у остальных схем они описаны в их разделах.

## Транспорт

Параметр `type` (у JSON-формы vmess — поле `net`) выбирает транспорт; остальные параметры читаются по нему.

Схемы, если в строке не сказано иное: `trojan`, `vless`, `vmess`.

| Ключ URL | Параметр config.json | Значения и пример |
|---|---|---|
| `type`<br>`headerType` | — | **Не читается.** tcp, raw или без параметра (регистр не важен) при headerType=none или без него: обычный TCP, блок transport не пишется.<br>Пример: `?type=tcp&headerType=none`<br>Протокол идёт прямо по TCP или TLS, без транспорта V2Ray. |
| `headerType`<br>`type` | `transport.type` | headerType=http при type=tcp (raw, пусто) и без TLS: пишется транспорт http.<br>Пример: `?type=tcp&headerType=http`<br>В outbound: `transport.type: "http"`<br>HTTP-заголовок транспорта TCP у Xray: строка запроса и заголовки перед потоком. Без TLS транспорт http в sing-box говорит так же, по HTTP/1.1. |
| `host` | `transport.host` | При TCP с headerType=http — список узлов через запятую.<br>Пример: `?type=tcp&headerType=http&host=cdn.example.org%2Cexample.org`<br>В outbound: `transport.host: ["cdn.example.org", "example.org"]`<br>Значения заголовка Host запроса. | `path` | `transport.path` | При TCP с headerType=http — путь запроса. Из списка через запятую берётся первый.<br>Пример: `?type=tcp&headerType=http&path=%2Fa%2C%2Fb`<br>В outbound: `transport.path: "/a"`<br>Xray принимает список путей и запрашивает случайный из них; в sing-box путь один. |
| `headerType`<br>`security` | — | **Отказ.** headerType=http вместе с TLS или REALITY.<br>Пример: `?security=tls&type=tcp&headerType=http`<br>Сообщение: `is not supported together with TLS`<br>С TLS транспорт http в sing-box говорит по HTTP/2, а это другой протокол. | `host` | `transport.headers.Host` | При ws — заголовок Host.<br>Пример: `?type=ws&host=cdn.example.org`<br>В outbound: `transport.headers.Host: "cdn.example.org"`<br>Имя сайта, по которому обратный прокси или CDN находит сервер. |

| `path` | `transport.path` | При http и h2 — путь запроса, как есть.<br>Пример: `?security=tls&type=http&path=%2Fh2`<br>В outbound: `transport.path: "/h2"`<br>Путь, по которому сервер ждёт соединения. |
| `method` | `transport.method` | При http и h2 — метод запроса, как есть.<br>Пример: `?security=tls&type=http&method=GET`<br>В outbound: `transport.method: "GET"`<br>Без параметра опция не пишется, и sing-box шлёт PUT. |
| `type`<br>`security` | — | **Предупреждение.** http или h2 в ссылке без TLS.<br>Пример: `?type=h2&path=%2Fh2`<br>Сообщение: `the HTTP/2 transport without TLS is spoken as HTTP/1.1`<br>Xray говорит здесь по HTTP/2 без шифрования, sing-box — по HTTP/1.1. Сервер на sing-box принимает и то и другое, сервер Xray не ответит. |
| `type` | `transport.type` | httpupgrade.<br>Пример: `?type=httpupgrade`<br>В outbound: `transport.type: "httpupgrade"`<br>При TLS параметр alpn для этого транспорта отбрасывается. |
| `host` | `transport.host` | При httpupgrade — имя узла, одной строкой как есть.<br>Пример: `?type=httpupgrade&host=cdn.example.org`<br>В outbound: `transport.host: "cdn.example.org"`<br>Значение заголовка Host запроса. |
| `path` | `transport.path` | При httpupgrade — путь запроса; «?ed=…» из него вырезается.<br>Пример: `?type=httpupgrade&path=%2Fup`<br>В outbound: `transport.path: "/up"`<br>Путь, по которому сервер ждёт соединения. |
| `ed`<br>`path` | — | **Предупреждение.** При httpupgrade: ed или «?ed=число» в пути.<br>Пример: `?type=httpupgrade&path=%2Fup%3Fed%3D2560`<br>Сообщение: `early data is not supported with the httpupgrade transport and is not sent`<br>Xray умеет ранние данные и здесь, sing-box — нет. Путь записывается без «?ed=». |
| `type`<br>`fp`<br>`alpn` | `transport.type` | quic — транспорт QUIC. Блок tls.utls при нём не пишется, каким бы ни был fp; без alpn в ссылке пишется tls.alpn = h3, h2, http/1.1.<br>Пример: `?security=tls&fp=chrome&type=quic`<br>В outbound: `transport.type: "quic", tls.alpn: ["h3", "h2", "http/1.1"]`<br>У QUIC свой TLS, и браузеру там не подражают: с uTLS каждое соединение рвалось бы. Без ALPN Xray предлагает h2 и http/1.1, а sing-box — h3; сервер каждого вида берёт только своё. |
| `alpn`<br>`type` | `tls.alpn` | При quic список из alpn записывается как есть, вместо списка по умолчанию.<br>Пример: `?security=tls&type=quic&alpn=h3%2Ch2`<br>В outbound: `tls.alpn: ["h3", "h2"]`<br>В отличие от ws, grpc, http и httpupgrade, здесь alpn из ссылки сохраняется. |
| `quicSecurity`<br>`key`<br>`headerType` | — | **Не читается.** При quic: quicSecurity=none, headerType=none и любой key читаются и отбрасываются.<br>Пример: `?security=tls&type=quic&quicSecurity=none&key=0123abcd&headerType=none`<br>Так ссылки записывают QUIC без шифрования и маскировки пакетов. |
| `quicSecurity` | — | **Отказ.** При quic: любое значение, кроме none.<br>Пример: `?security=tls&type=quic&quicSecurity=aes-128-gcm&key=0123abcd`<br>Сообщение: `the encryption of the QUIC transport (quicSecurity) is not supported`<br>Шифрования пакетов транспорта QUIC из V2Ray в sing-box нет. |
| `headerType`<br>`type` | — | **Отказ.** При quic: любое значение, кроме none.<br>Пример: `?security=tls&type=quic&headerType=wechat-video`<br>Сообщение: `the packet header of the QUIC transport (headerType) is not supported`<br>Маскировки пакетов транспорта QUIC из V2Ray в sing-box нет. |
| `type`<br>`security` | — | **Отказ.** quic в ссылке без TLS.<br>Пример: `?type=quic`<br>Сообщение: `TLS required`<br>Декодер такую ссылку пропускает; отказывает sing-box при сборке outbound: QUIC без TLS не бывает. |
| `type` | — | **Отказ.** kcp или mkcp.<br>Пример: `?type=kcp`<br>Сообщение: `the mKCP transport is not supported`<br>Транспорта mKCP в sing-box нет. |
| `seed`<br>`mtu`<br>`tti` | — | **Не читается.** Настройки mKCP. С любым другим транспортом читаются и отбрасываются.<br>Пример: `?type=tcp&seed=0123abcd&mtu=1350&tti=50`<br>Сам mKCP — отказ; а оставшись в ссылке с другим транспортом, эти параметры предупреждений не дают. |
| `type` | — | **Отказ.** Любое другое значение.<br>Пример: `?type=h3`<br>Сообщение: `unsupported transport`<br>Транспорт xhttp (splithttp) описан отдельно. |
| `host`<br>`path`<br>`method`<br>`serviceName`<br>`mode`<br>`authority`<br>`ed`<br>`eh`<br>`headerType`<br>`quicSecurity`<br>`key` | — | **Не читается.** Параметр, который выбранному транспорту не нужен, читается и отбрасывается: например host и path при обычном TCP.<br>Пример: `?type=tcp&host=cdn.example.org&path=%2F`<br>Эти имена декодер знает при любом транспорте, поэтому предупреждений о них нет. |

## Настройки клиента в ссылке

Параметры, которыми панели и клиенты передают настройки самого клиента: фрагментацию, шум, мультиплексирование.

Схемы, если в строке не сказано иное: `trojan`, `vless`, `vmess`.

| Ключ URL | Параметр config.json | Значения и пример |
|---|---|---|
| `fragment` | — | **Предупреждение.** Любое непустое значение.<br>Пример: `?fragment=100-200%2C10-20%2Ctlshello`<br>Сообщение: `fragment is a setting of the client of Xray and is not applied`<br>Как клиент Xray дробит свои пакеты; сервер от этого не зависит. Дробление самого sing-box включает sb.tls.fragment=1. |
| `noise`<br>`noises` | — | **Предупреждение.** Любое непустое значение.<br>Пример: `?noise=rand`<br>Сообщение: `noise is a setting of the client of Xray and is not applied`<br>Шумовые пакеты клиента Xray; сервер от них не зависит. |
| `fm` | — | **Предупреждение.** JSON finalmask Xray, в списках tcp и udp которого только маски fragment и noise.<br>Пример: `?fm=%7B%22tcp%22%3A%5B%7B%22type%22%3A%22fragment%22%7D%5D%7D`<br>Сообщение: `fm (finalmask) is not supported and is ignored`<br>Эти маски — дело самого клиента: до сервера можно дойти и без них. |
| `fm` | — | **Предупреждение.** Значение, которое не читается как JSON.<br>Пример: `?fm=x`<br>Сообщение: `fm (finalmask) is not supported and cannot be read`<br>Что просила ссылка, неизвестно: связь может и не заработать. |
| `fm` | — | **Отказ.** В списке tcp или udp есть любая другая маска.<br>Пример: `?fm=%7B%22tcp%22%3A%5B%7B%22type%22%3A%22header-custom%22%7D%5D%7D`<br>Сообщение: `fm (finalmask) asks for the mask`<br>Такая маска меняет то, что идёт по сети, и сервер её ждёт: без неё связи не будет. |
| `heartbeatPeriod` | — | **Не читается.** Любое значение читается и отбрасывается.<br>Пример: `?type=ws&path=%2Fws&heartbeatPeriod=30`<br>Как часто клиент Xray шлёт ping по WebSocket — его собственное дело. |
| `mux` | — | **Предупреждение.** Любое значение.<br>Пример: `?mux=1`<br>Сообщение: `mux is not supported and is ignored`<br>Клиенты понимают голое mux по-разному, поэтому оно не читается, как и любой неизвестный параметр. Понятные имена — mux_protocol и соседние. |
| `mux_protocol` | `multiplex.protocol` | Текст как есть; sing-box знает h2mux, smux и yamux.<br>Пример: `?mux_protocol=h2mux&sb.multiplex.enabled=1`<br>В outbound: `multiplex.protocol: "h2mux", multiplex.enabled: true`<br>Имена мультиплексирования из клиента Throne. Имени для самого включения нет: его даёт sb.multiplex.enabled=1. |
| `mux_max_connections` | `multiplex.max_connections` | Целое число.<br>Пример: `?mux_max_connections=4&sb.multiplex.enabled=1`<br>В outbound: `multiplex.max_connections: 4`<br>Наибольшее число соединений мультиплексирования. Не число — отказ «does not fit the option». |
| `mux_min_streams` | `multiplex.min_streams` | Целое число.<br>Пример: `?mux_min_streams=4&sb.multiplex.enabled=1`<br>В outbound: `multiplex.min_streams: 4`<br>Сколько потоков должно набраться в соединении, прежде чем откроется новое. |
| `mux_max_streams` | `multiplex.max_streams` | Целое число.<br>Пример: `?mux_max_streams=8&sb.multiplex.enabled=1`<br>В outbound: `multiplex.max_streams: 8`<br>Наибольшее число потоков в одном соединении. |
| `mux_padding` | `multiplex.padding` | 1 или true — true; 0 или false — false.<br>Пример: `?mux_padding=1&sb.multiplex.enabled=1`<br>В outbound: `multiplex.padding: true`<br>Дополнение пакетов мультиплексирования. Другое значение — отказ «does not fit the option». |
| `brutal_up_mbps` | `multiplex.brutal.up_mbps` | Целое число, Мбит/с.<br>Пример: `?brutal_up_mbps=50&brutal_down_mbps=100&sb.multiplex.enabled=1&sb.multiplex.brutal.enabled=1`<br>В outbound: `multiplex.brutal.up_mbps: 50, multiplex.brutal.enabled: true`<br>Скорость отдачи для TCP Brutal. Его включает sb.multiplex.brutal.enabled=1, и тогда нужны обе скорости. |
| `brutal_down_mbps` | `multiplex.brutal.down_mbps` | Целое число, Мбит/с.<br>Пример: `?brutal_up_mbps=50&brutal_down_mbps=100&sb.multiplex.enabled=1&sb.multiplex.brutal.enabled=1`<br>В outbound: `multiplex.brutal.down_mbps: 100, multiplex.brutal.enabled: true`<br>Скорость приёма для TCP Brutal. |
| `mux_protocol`<br>`mux_max_connections`<br>`mux_min_streams`<br>`mux_max_streams`<br>`mux_padding`<br>`brutal_up_mbps`<br>`brutal_down_mbps` | — | **Предупреждение.** Имена mux_… и brutal_… без включения: опции записываются, но sing-box ими не пользуется.<br>Пример: `?mux_protocol=h2mux`<br>Сообщение: `multiplex has options and is not enabled`<br>Для brutal_… такое же предупреждение про multiplex.brutal. Лекарство названо в самом сообщении: sb.multiplex.enabled=1. |

## XHTTP: параметры ссылки

Транспорт XHTTP (`type=xhttp`; `splithttp` — прежнее имя). Его настройки приходят параметрами ссылки и в JSON параметра `extra`.

Схемы, если в строке не сказано иное: `trojan`, `vless`, `vmess`.

| Ключ URL | Параметр config.json | Значения и пример |
|---|---|---|
| `type` | `transport.type` | xhttp или splithttp (другое имя того же транспорта), регистр не важен; в конфигурацию пишется xhttp.<br>Пример: `?type=xhttp`<br>В outbound: `transport.type: "xhttp"`<br>Включает транспорт XHTTP из Xray; все остальные строки трёх разделов описывают ссылку с таким type. |
| `path` | `transport.path` | Строка как есть; без параметра опция не пишется.<br>Пример: `?type=xhttp&path=%2Fapi%2F`<br>В outbound: `transport.path: "/api/"`<br>Путь запросов на сервере. Берётся только из самой ссылки, path внутри extra не читается; часть после «?» sing-box отправляет как строку запроса. |
| `host` | `transport.host` | Строка как есть; без параметра опция не пишется.<br>Пример: `?type=xhttp&host=cdn.example.org`<br>В outbound: `transport.host: "cdn.example.org"`<br>Заголовок Host запросов. Берётся только из самой ссылки; если параметра нет, берётся Host из extra.headers, а без него sing-box подставляет tls.server_name или адрес сервера. |
| `mode`<br>`xhttpMode` | `transport.mode` | auto, packet-up, stream-up или stream-one, пишется как есть; из двух имён берётся первое непустое, сначала mode; без параметра — auto, опция не пишется.<br>Пример: `?type=xhttp&mode=packet-up`<br>В outbound: `transport.mode: "packet-up"`<br>Как клиент отправляет данные: packet-up — отдельными запросами, stream-up и stream-one — потоком; при auto sing-box берёт packet-up, с REALITY — stream-one (stream-up, если есть downloadSettings). xhttpMode — имя из ссылок v2rayA; mode внутри extra не читается. |
| `mode`<br>`xhttpMode` | — | **Отказ.** Любое другое значение, в том числе верное имя в другом регистре (Auto)<br>Пример: `?type=xhttp&mode=stream-down`<br>Сообщение: `unsupported mode`<br>Декодер пишет mode как есть; отказывает проверка транспорта при сборке outbound: «error: xhttp: unsupported mode: stream-down». |
| `extra` | `transport` | JSON-объект с настройками XHTTP под именами Xray, URL-экранированный; пробел — %20 или «+»; поля — в разделе xhttp-extra.<br>Пример: `?type=xhttp&extra=%7B%22xPaddingBytes%22:%22100-1000%22%7D`<br>В outbound: `transport.x_padding_bytes: "100-1000"`<br>Так панели Xray (3x-ui, Marzban, Hiddify) передают настройки XHTTP, у которых нет своего параметра. Внутри JSON «+» пишется как %2B, «&» как %26, «#» как %23. |
| `extra` | `transport` | То же, экранированное дважды: если после первого снятия экранирования значение начинается с %7B, экранирование снимается ещё раз.<br>Пример: `?type=xhttp&extra=%257B%2522noGRPCHeader%2522:true%257D`<br>В outbound: `transport.no_grpc_header: true`<br>Так extra записывают некоторые панели и клиенты; результат тот же. |
| `extra` | — | **Отказ.** JSON, но не объект: строка, число, список.<br>Пример: `?type=xhttp&extra=%22text%22`<br>Сообщение: `read extra: not a JSON object`<br>Содержимое extra в ошибке не повторяется: ссылка — секрет. |
| `extra` | — | **Отказ.** Оборванный или неверный JSON.<br>Пример: `?type=xhttp&extra=%7B%22xPaddingBytes%22:`<br>Сообщение: `read extra: unexpected end of JSON input`<br>Так читается extra, обрезанное при копировании или оборванное неэкранированным «&» либо «#». |
| `x_padding_bytes` | `transport.x_padding_bytes` | «от-до» или одно число; читается, только если в extra нет xPaddingBytes; параметр xPaddingBytes той же ссылки его перекрывает.<br>Пример: `?type=xhttp&x_padding_bytes=200-300`<br>В outbound: `transport.x_padding_bytes: "200-300"`<br>Под этим именем панель 3x-ui повторяет вне extra размер случайной добавки к запросам (padding). |
| `x_padding_bytes` | — | **Отказ.** Не число и не «от-до»<br>Пример: `?type=xhttp&x_padding_bytes=a-b`<br>Сообщение: `invalid range in the link parameter x_padding_bytes`<br>Проверяется, даже когда рядом есть параметр xPaddingBytes; не проверяется, только если xPaddingBytes назван в extra. |
| `xPaddingBytes`<br>`sessionIDLength`<br>`uplinkChunkSize`<br>`scMaxEachPostBytes`<br>`scMinPostsIntervalMs`<br>`scStreamUpServerSecs` | `transport` | Каждое имя — отдельная настройка: «от-до» или одно число, пишется в ту же опцию, что одноимённое поле extra; 0 — опция не пишется.<br>Пример: `?type=xhttp&xPaddingBytes=100-1000&sessionIDLength=16-32&uplinkChunkSize=3000-4000&scMaxEachPostBytes=500000&scMinPostsIntervalMs=10-50&scStreamUpServerSecs=20-80`<br>Настройки XHTTP прямо параметрами ссылки, под именами Xray, пишут некоторые генераторы, среди них панель 3x-ui. Смысл каждой описан в разделе xhttp-extra. |
| `xPaddingBytes`<br>`sessionIDLength`<br>`uplinkChunkSize`<br>`scMaxEachPostBytes`<br>`scMinPostsIntervalMs`<br>`scStreamUpServerSecs` | — | **Отказ.** Любой из этих параметров со значением, которое не число и не «от-до»<br>Пример: `?type=xhttp&xPaddingBytes=a-b`<br>Сообщение: `invalid range in the link parameter`<br>Имя параметра в ошибке — строчными буквами: «… the link parameter xpaddingbytes». |
| `xPaddingKey`<br>`xPaddingHeader`<br>`xPaddingPlacement`<br>`xPaddingMethod`<br>`uplinkHTTPMethod`<br>`sessionIDPlacement`<br>`sessionPlacement`<br>`sessionIDKey`<br>`sessionKey`<br>`sessionIDTable`<br>`seqPlacement`<br>`seqKey`<br>`uplinkDataPlacement`<br>`uplinkDataKey` | `transport` | Каждое имя — отдельная настройка: строка как есть, пишется в ту же опцию, что одноимённое поле extra; sessionPlacement и sessionKey — прежние имена sessionIDPlacement и sessionIDKey, из пары берётся новое.<br>Пример: `?type=xhttp&mode=packet-up&xPaddingKey=pad&xPaddingHeader=X-Pad&xPaddingPlacement=cookie&xPaddingMethod=tokenish&uplinkHTTPMethod=PUT&sessionIDPlacement=header&sessionIDKey=X-Sid&sessionIDTable=hex&sessionIDLength=16-32&seqPlacement=query&seqKey=seq&uplinkDataPlacement=header&uplinkDataKey=X-Up`<br>Допустимые значения те же, что у полей extra: неподходящее (например, размещение, которого нет) отвергается при сборке outbound. |
| `xPaddingObfsMode`<br>`noGRPCHeader`<br>`noSSEHeader` | `transport` | Каждое имя — отдельная настройка: 1 или true в любом регистре — включено; иное — выключено, опция не пишется.<br>Пример: `?type=xhttp&xPaddingObfsMode=true&noGRPCHeader=1&noSSEHeader=true`<br>В outbound: `transport.x_padding_obfs_mode: true, transport.no_grpc_header: true, transport.no_sse_header: true`<br>Те же настройки, что одноимённые поля extra; там это true и false, в параметре ссылки — текст. |
| `scMaxBufferedPosts`<br>`serverMaxHeaderBytes` | `transport` | Каждое имя — отдельная настройка: целое число; 0 — опция не пишется.<br>Пример: `?type=xhttp&scMaxBufferedPosts=30&serverMaxHeaderBytes=8192`<br>В outbound: `transport.sc_max_buffered_posts: 30, transport.server_max_header_bytes: 8192`<br>Обе — настройки сервера: в конфигурацию переносятся, клиент sing-box их не использует. |
| `scMaxBufferedPosts`<br>`serverMaxHeaderBytes` | — | **Отказ.** Любой из этих параметров, если значение не целое число или больше 2147483647.<br>Пример: `?type=xhttp&scMaxBufferedPosts=many`<br>Сообщение: `invalid number in the link parameter`<br>Имя параметра в ошибке — строчными буквами: «… the link parameter scmaxbufferedposts». |
| `xPaddingBytes` | — | **Не читается.** Любой параметр XHTTP вне extra (здесь xPaddingBytes), когда то же поле названо в extra, пусть даже как false, 0 или пустая строка.<br>Пример: `?type=xhttp&xPaddingBytes=5-9&extra=%7B%22xPaddingBytes%22:%221-2%22%7D`<br>Названное в extra решает extra, без предупреждения. Для пар sessionPlacement/sessionIDPlacement и sessionKey/sessionIDKey достаточно любого из двух имён в extra. |
| `alpn` | `tls.alpn` | Список через запятую; с type=xhttp остаётся как в ссылке (с ws, grpc, http и httpupgrade декодер его убирает)<br>Пример: `?security=tls&sni=example.org&alpn=h2%2Chttp%2F1.1&type=xhttp`<br>В outbound: `tls.alpn: ["h2", "http/1.1"]`<br>По ALPN транспорт выбирает версию HTTP: одно значение http/1.1 — HTTP/1.1, одно h3 — HTTP/3, иначе HTTP/2; с REALITY всегда HTTP/2, без TLS — HTTP/1.1. |
| `flow`<br>vless | — | **Отказ.** xtls-rprx-vision или xtls-rprx-vision-udp443 вместе с type=xhttp и без шифрования VLESS.<br>Пример: `?security=tls&type=xhttp&flow=xtls-rprx-vision`<br>Сообщение: `is not supported over the xhttp transport`<br>Vision нужен сам канал TLS; поверх XHTTP сервер Xray принимает flow только с шифрованием VLESS (параметр encryption, с r14 он читается). |
| `net`<br>vmess | `transport.type` | Ссылка VMess вида base64(JSON): net равно xhttp или splithttp; для этого транспорта из JSON читаются только host и path.<br>Пример: `{"add":"example.org","port":"443","id":"6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11","net":"xhttp","host":"cdn.example.org","path":"/api/"}`<br>В outbound: `transport.type: "xhttp", transport.host: "cdn.example.org", transport.path: "/api/"`<br>Форма v2rayN. mode и extra в ней не передать: поле type с этим транспортом не читается. В виде vmess://uuid@host:port?type=xhttp&… действуют все строки раздела. |

## XHTTP: поля extra

В первом столбце — имена полей JSON из параметра `extra`, вложенные через точку. В примерах показан сам JSON; в ссылке он закодирован (`%7B…%7D`).

Схемы, если в строке не сказано иное: `trojan`, `vless`, `vmess`.

| Ключ URL | Параметр config.json | Значения и пример |
|---|---|---|
| `host`<br>`path`<br>`mode` | — | **Не читается.** Любое значение любого из трёх полей.<br>Пример: `extra={"host":"other.example.org","path":"/other","mode":"stream-one"}`<br>Как в Xray, host, path и mode берутся только из самой ссылки, даже когда в ссылке их нет, а в extra есть; предупреждения нет. |
| `headers` | `transport.headers.<name>` | Объект «имя: строка»; каждый заголовок, кроме Host, пишется под своим именем; значение не строкой — отказ «headers has a value of the wrong type»<br>Пример: `extra={"headers":{"User-Agent":"Mozilla/5.0"}}`<br>В outbound: `transport.headers.User-Agent: "Mozilla/5.0"`<br>Свои заголовки запросов. По умолчанию sing-box добавляет заголовки как у Chrome; User-Agent со значением firefox, safari, edge, curl или golang выбирает другого клиента, любое иное значение отправляется как есть. |

| `headers.Host` | — | **Предупреждение.** Значение, отличное от параметра host ссылки; совпадающее отбрасывается молча.<br>Пример: `extra={"headers":{"Host":"other.example.org"}}`<br>Сообщение: `the Host header is ignored, the host of the link is used`<br>Остаётся host ссылки. | `xPaddingBytes` | — | **Отказ.** Не читается как диапазон: «a-b», 30.5.<br>Пример: `extra={"xPaddingBytes":"a-b"}`<br>Сообщение: `invalid range`<br>Так же отказывают остальные диапазоны в extra, xmux и downloadSettings; значение в ошибке не повторяется. |
| `xPaddingBytes` | — | **Отказ.** Диапазон с нуля или с отрицательного числа («0-100»); верхняя граница больше 65536 — отказ «x_padding_bytes is too large»<br>Пример: `extra={"xPaddingBytes":"0-100"}`<br>Сообщение: `x_padding_bytes cannot be disabled`<br>Проверка транспорта при сборке outbound. | `xPaddingObfsMode` | `transport.x_padding_obfs_mode` | true или false значением JSON, не строкой; false не пишется.<br>Пример: `extra={"xPaddingObfsMode":true}`<br>В outbound: `transport.x_padding_obfs_mode: true`<br>Включает своё размещение добавки: без него xPaddingKey, xPaddingHeader, xPaddingPlacement и xPaddingMethod не действуют, а добавка идёт в заголовке Referer. |

| `sessionIDTable`<br>`sessionIDLength` | `transport` | Каждое имя — отдельная настройка: sessionIDTable → session_id_table: имя готового набора (hex, HEX, number, alphabet, Alphabet, ALPHABET, base36, BASE36, Base62) или свой набор из латинских букв, цифр и -._~; sessionIDLength → session_id_length: диапазон или число от 1 до 1024.<br>Пример: `extra={"sessionIDTable":"hex","sessionIDLength":"16-32"}`<br>В outbound: `transport.session_id_table: "hex", transport.session_id_length: "16-32"`<br>Из каких символов и какой длины составлять идентификатор сессии; без sessionIDTable это UUID, а sessionIDLength не действует. |

| `extra` | — | **Не читается.** Любое значение.<br>Пример: `extra={"extra":{"xPaddingBytes":"100-1000"}}`<br>Вложенный extra читается только внутри downloadSettings.xhttpSettings; здесь он отбрасывается без предупреждения. |
| `<other>` | — | **Предупреждение.** Любое поле, которого нет в разделах xhttp-extra и xhttp-download.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?type=xhttp&extra=%7B%22future%22:1%7D`<br>Сообщение: `extra: future is not supported and is ignored`<br>Xray незнакомые поля пропускает молча; декодер их называет, потому что молча отброшенная настройка — частая причина «ссылка не работает». |

| `<имя поля>` | — | **Предупреждение.** Имя поля в JSON — не имя: в нём есть что-то кроме латинских букв, цифр, «-», «_» и «.».<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?type=xhttp&security=tls&extra=%7B%22bad%20name%22%3A1%7D`<br>Сообщение: `extra: a key that is not a name is ignored`<br>В outbound: `transport.type: "xhttp"`<br>Поле отбрасывается, и его имя в сообщении не повторяется — как имя параметра ссылки, которое не является именем. ## XHTTP: отдельный сервер приёма

Поле `downloadSettings` в `extra` описывает второй сервер, с которого идёт приём. В первом столбце — имена полей внутри `extra`.

Схемы, если в строке не сказано иное: `trojan`, `vless`, `vmess`.

| Ключ URL | Параметр config.json | Значения и пример |
|---|---|---|
| `downloadSettings.address`<br>`downloadSettings.port` | `transport.download` | Каждое имя — отдельная настройка: address → server: имя или IP-адрес, квадратные скобки вокруг IPv6 снимаются; port → server_port: число от 1 до 65535, не строкой.<br>Пример: `extra={"downloadSettings":{"address":"cdn.example.org","port":443}}`<br>В outbound: `transport.download.server: "cdn.example.org", transport.download.server_port: 443`<br>Отдельный сервер, с которого идёт приём данных (отправка идёт через основной). От основной части ссылки он ничего не наследует: TLS, host, path и остальное задаются только в downloadSettings. |
| `downloadSettings.address`<br>`downloadSettings.port` | — | **Отказ.** Нет адреса («missing address») или порта («missing port»), либо порт равен 0.<br>Пример: `extra={"downloadSettings":{"address":"cdn.example.org"}}`<br>Сообщение: `downloadSettings: missing port`<br>Адрес и порт основного сервера на их место не подставляются. |

## Shadowsocks

Ссылки `ss://`: вид SIP002 (`ss://base64(метод:пароль)@узел:порт`) и старый вид (`ss://base64(метод:пароль@узел:порт)`).

Схемы, если в строке не сказано иное: `ss`.

| Ключ URL | Параметр config.json | Значения и пример |
|---|---|---|
| `<user>` | `method` | SIP002: часть до @ — base64 от «метод:пароль» (URL-алфавит или обычный, с «=» или без). Метод — до первого двоеточия, в нижнем регистре; chacha20-poly1305 и xchacha20-poly1305 записываются как chacha20-ietf-poly1305 и xchacha20-ietf-poly1305.<br>Пример: `ss://YWVzLTI1Ni1nY206c2VjcmV0@example.org:8388`<br>В outbound: `type: "shadowsocks", method: "aes-256-gcm", password: "secret"`<br>Обычный вид ссылки Shadowsocks. Метод должен быть известен sing-box (aes-*-gcm, chacha20-ietf-poly1305, xchacha20-ietf-poly1305, 2022-blake3-*, старые потоковые): иначе outbound не собирается — «unknown method». |
| `<user>` | `method` | SIP002 без base64: «метод:пароль» открытым текстом. %-кодирование снимается; «/», «+», «=» ключа читаются и без него.<br>Пример: `ss://2022-blake3-aes-128-gcm:MDEyMzQ1Njc4OWFiY2RlZg%3D%3D@example.org:8388`<br>В outbound: `method: "2022-blake3-aes-128-gcm", password: "MDEyMzQ1Njc4OWFiY2RlZg=="`<br>Так пишут методы 2022-blake3-*. Признак открытого текста — двоеточие в части до @; без него она читается как base64. |
| `<user>` | `method` | Старая форма: всё между «ss://» и «#» — base64 от «метод:пароль@хост:порт».<br>Пример: `ss://YWVzLTI1Ni1nY206c2VjcmV0QGV4YW1wbGUub3JnOjgzODg#old`<br>В outbound: `tag: "old", method: "aes-256-gcm", password: "secret", server: "example.org", server_port: 8388`<br>Вид ссылок до SIP002; узнаётся по отсутствию @ в самой ссылке. «%» в пароле такой ссылки — обычный символ. |
| `<password>` | `password` | Текст после первого двоеточия в «метод:пароль»; остальные двоеточия остаются в пароле.<br>Пример: `ss://YWVzLTI1Ni1nY206cGFzczp3b3Jk@example.org:8388`<br>В outbound: `password: "pass:word"`<br>У методов 2022 пароль — ключ в base64 (или «ключ_сервера:ключ_пользователя»); ключ неверной длины sing-box отвергает. |
| `<user>` | — | **Отказ.** Нет двоеточия ни в открытом виде, ни после раскодирования base64; пустой метод; метод не из латинских букв, цифр, «-», «_», «.» или длиннее 40 знаков.<br>Пример: `ss://c2VjcmV0@example.org:8388`<br>Сообщение: `the user of the link is not a method and a password`<br>Сообщение не повторяет часть до @: на месте метода может оказаться пароль. |
| `<host>`<br>`<port>` | `server` | Имя или IP-адрес (IPv6 в скобках) → server; порт → server_port, обязателен (без него — missing server port). После порта допускается «/».<br>Пример: `ss://YWVzLTI1Ni1nY206c2VjcmV0@192.0.2.1:8388`<br>В outbound: `server: "192.0.2.1", server_port: 8388`<br>Адрес и порт сервера; порта по умолчанию у ссылки Shadowsocks нет. |
| `plugin` | `plugin` | «имя;опция;опция» (SIP003): имя до первой «;» → plugin, остальное без изменений → plugin_opts. Имя simple-obfs записывается как obfs-local.<br>Пример: `?plugin=simple-obfs%3Bobfs%3Dhttp%3Bobfs-host%3Dcdn.example.org`<br>В outbound: `plugin: "obfs-local", plugin_opts: "obfs=http;obfs-host=cdn.example.org"`<br>Плагин обфускации. В sing-box их два: obfs-local (прежнее имя simple-obfs) и v2ray-plugin; с другим именем outbound не собирается — «plugin not found». Опции плагина разборщик не проверяет. |
| `uot`<br>`udp-over-tcp` | `udp_over_tcp` | 1 или true → true. Другое значение (0, false, 2) ничего не включает и предупреждения не даёт.<br>Пример: `?uot=1`<br>В outbound: `udp_over_tcp: true`<br>UDP поверх TCP-соединения с сервером (UDP over TCP sing-box); имена параметра пришли из mihomo. |
| `type`<br>`security`<br>`headerType` | — | **Не читается.** type пусто, tcp или raw; security и headerType пусто или none — принимается и ничего не меняет. Иное — отказ shadowsocks-transport.<br>Пример: `?type=tcp&security=none&headerType=none`<br>Параметры из ссылок панелей Xray: Xray умеет Shadowsocks поверх своих транспортов и TLS. |
| `#name`<br>ss, socks, socks4, socks4a, socks5, socks5h, http, https, hysteria2, hy2, hysteria, tuic, anytls, naive+https, naive+quic | `tag` | Текст после первого «#»; %-кодирование снимается, пробелы по краям отбрасываются. Без имени tag не пишется.<br>Пример: `ss://YWVzLTI1Ni1nY206c2VjcmV0@example.org:8388#My%20server`<br>В outbound: `tag: "My server"`<br>Имя сервера, становится тегом outbound; одинаково у всех схем. |

## Любая опция по её пути: sb.<путь>

Опцию outbound, для которой у ссылок нет общепринятого параметра, задаёт параметр `sb.<путь опции>=<значение>`: путь — как в config.json, через точки. Такой параметр сильнее того, что ссылка говорит об этой же опции иначе.

Схемы, если в строке не сказано иное: `anytls`, `http`, `https`, `hy2`, `hysteria`, `hysteria2`, `naive+https`, `naive+quic`, `socks`, `socks4`, `socks4a`, `socks5`, `socks5h`, `ss`, `trojan`, `tuic`, `vless`, `vmess`.

| Ключ URL | Параметр config.json | Значения и пример |
|---|---|---|
| `sb.<path>` | `tls.fragment` | Путь после «sb.» — путь опции outbound в config.json через точки; имена опций пишутся в любом регистре. Тип значения берётся из типа опции в этой сборке sing-box. Флаг: 1 или true → true, 0 или false → false (false записывается явно).<br>Пример: `trojan://secret@example.org:443?sb.tls.fragment=1`<br>В outbound: `tls.fragment: true`<br>Способ задать опцию sing-box, для которой у ссылок нет своего параметра. Один параметр — одна опция; путь главнее всего остального, что сказано в ссылке. |
| `sb.<path>` | `multiplex.max_connections` | Число: записывается как написано; для целой опции дробь или не число — отказ sb-value.<br>Пример: `trojan://secret@example.org:443?sb.multiplex.enabled=1&sb.multiplex.max_connections=4`<br>В outbound: `multiplex.enabled: true, multiplex.max_connections: 4`<br>Пример числа. Группу опций с выключателем (multiplex, tls, tls.ech…) надо включить отдельно: sb.<группа>.enabled=1. |
| `sb.<path>` | `connect_timeout` | Длительность: число с единицей ns, us, ms, s, m, h или d (5s, 500ms, 1h30m), записывается как написано. Голое число — отказ sb-value.<br>Пример: `socks5://192.0.2.1:1080?sb.connect_timeout=5s`<br>В outbound: `connect_timeout: "5s"`<br>Пример длительности: сколько ждать установления соединения. |
| `sb.<path>` | `tls.min_version` | Строка: записывается как есть, даже если похожа на число.<br>Пример: `trojan://secret@example.org:443?sb.tls.min_version=1.3`<br>В outbound: `tls.min_version: "1.3"`<br>Пример строки. Годится ли само значение, решает sing-box при сборке outbound: негодное даёт его ошибку и статус 2. |
| `sb.<path>` | `tls.alpn` | Список: элементы через запятую (пробелы вокруг отбрасываются) или JSON-массив простых значений — sb.tls.alpn=%5B%22h2%22%5D.<br>Пример: `trojan://secret@example.org:443?sb.tls.alpn=h2,http/1.1`<br>В outbound: `tls.alpn: ["h2", "http/1.1"]`<br>Пример списка. Вид JSON нужен, когда в самих элементах есть запятые. |
| `sb.<path>.<name>` | `transport.headers.User-Agent` | Запись словаря (заголовок): имя — последняя часть пути, регистр сохраняется; значение берётся целиком, по запятым не делится. Без имени записи (sb.transport.headers=…) — отказ sb-unknown.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?type=ws&sb.transport.headers.User-Agent=curl%2F8`<br>В outbound: `transport.headers.User-Agent: ["curl/8"]`<br>Так задаются заголовки: transport.headers.<Имя>, а у outbound http и naive — headers.<Имя> и extra_headers.<Имя>. |
| `sb.<path>` | `transport.path` | Опции структуры с несколькими видами (транспорт по его type, обфускация hysteria2 по obfs.type) ищутся среди опций выбранного вида; параметр sb.….type применяется раньше остальных. Опция другого вида (sb.transport.service_name при type=ws) — отказ sb-unknown.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?sb.transport.type=ws&sb.transport.path=%2Fws`<br>В outbound: `transport.type: "ws", transport.path: "/ws"`<br>Пример: транспорт задан целиком путями. |
| `sb.<path>` | — | **Предупреждение.** Задана опция группы с выключателем enabled, а сама группа не включена.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?sb.multiplex.protocol=smux`<br>Сообщение: `multiplex has options and is not enabled`<br>Outbound создаётся, опция записана, но sing-box её не использует, пока группа не включена. |
| `sb.<path>` | — | **Предупреждение.** Путь задаёт опцию, которую ссылка уже задала иначе — своим параметром или именем другого клиента.<br>Пример: `trojan://secret@example.org:443?sni=cdn.example.org&sb.tls.server_name=www.example.org`<br>Сообщение: `sb.tls.server_name replaces what the link sets otherwise`<br>Побеждает путь: в outbound идёт его значение. |
| `sb.server_ports`<br>hysteria2, hy2, hysteria | `server_ports` | Диапазоны портов в записи sing-box «от:до» через запятую. Без первого порта диапазон начинается с 0, без последнего кончается на 65535. Список, в котором названо больше 65535 портов, — отказ ports.<br>Пример: `hysteria2://secret@example.org:443?sb.server_ports=20000%3A`<br>В outbound: `server_ports: ["20000:"]`<br>Обычно порты задают в самой ссылке (host:порт1,порт2-порт3) или параметром mport; путём удобно задать открытый диапазон. |

## Что ссылке задавать нельзя

Ссылка приходит извне. Она настраивает то, как достучаться до её сервера, и не трогает остальное: другие объекты конфигурации, локальный маршрут, файлы, пределы времени этого узла.

Схемы, если в строке не сказано иное: `anytls`, `http`, `https`, `hy2`, `hysteria`, `hysteria2`, `naive+https`, `naive+quic`, `socks`, `socks4`, `socks4a`, `socks5`, `socks5h`, `ss`, `trojan`, `tuic`, `vless`, `vmess`.

| `sb.type`<br>`sb.tag`<br>`sb.server`<br>`sb.server_port` | — | **Отказ.** То, что ссылка говорит сама: тип outbound, его имя и адрес сервера.<br>Пример: `trojan://secret@example.org:443?sb.server=192.0.2.1`<br>Сообщение: `is not for a link parameter to set (the link)`<br>Адрес, порт, тип и имя берутся только из самой ссылки, параметром их подменить нельзя. |
| `sb.<path>` | — | **Отказ.** Значение — JSON-объект (в том числе внутри массива): он задал бы сразу несколько опций по именам, которые никто не проверил.<br>Пример: `trojan://secret@example.org:443?sb.multiplex=%7B%22enabled%22%3Atrue%7D`<br>Сообщение: `gives several options at once`<br>Отказ sb-value: иначе внутри объекта прошли бы и запрещённые имена — файл, detour. |

## Отказы по идентификаторам

Каждый отказ декодера имеет идентификатор; основание каждого записано в `common/sharelink/policy.go`. Отказ значит, что outbound из ссылки, как она есть, в sing-box не заработает.

| Ключ URL | Параметр config.json | Значения и пример |
|---|---|---|
| `<scheme>` | — | **Отказ.** no-link-form: ссылка со схемой tor://, ssh://, shadowtls:// или snell://.<br>Пример: `tor://example.org:9050`<br>Сообщение: `outbound has no link form`<br>Эти outbound настраиваются в конфигурации: ссылок для них никто не выпускает, а нужное им (второй outbound, файлы, ключи узла) ссылкой не передать. |
| `security` | — | **Отказ.** security: значение security, кроме none, tls и reality (например xtls).<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?security=xtls`<br>Сообщение: `unsupported security`<br>Такое значение называет защиту транспорта, которой в sing-box нет. |
| `fp` | — | **Отказ.** fingerprint-reality: при security=reality отпечаток unsafe или имя, которого не знают ни sing-box, ни Xray.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?security=reality&pbk=YBZ6SAP7KfiD5YJiyAGvD49eNYW-f-7IlhMarfyy4k0&sid=0123abcd&fp=netscape`<br>Сообщение: `which REALITY needs`<br>REALITY построен на uTLS и без отпечатка не работает; Xray неизвестный отпечаток отвергает тоже. |
| `encryption` | — | **Отказ.** vless-encryption: encryption начинается с mlkem768x25519plus, но такую настройку шифрования VLESS не принимает и Xray (режим, 1rtt или 0rtt, дополнение, ключи по 32 или 1184 байта).<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?encryption=mlkem768x25519plus.native.0rtt.KEY`<br>Сообщение: `invalid VLESS encryption`<br>Верная настройка с r14 записывается в опцию encryption. Другое непустое значение encryption читается как none, с предупреждением. |
| `flow` | — | **Отказ.** flow: значение flow, кроме xtls-rprx-vision и xtls-rprx-vision-udp443.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?security=tls&flow=xtls-rprx-direct`<br>Сообщение: `unsupported flow`<br>Других flow в sing-box нет, а старые Xray и сам убрал. |
| `flow`<br>`type`<br>`sb.flow`<br>`sb.transport.type` | — | **Отказ.** flow-transport: flow задан вместе с транспортом (ws, grpc, http, httpupgrade, xhttp, quic) — параметрами ссылки или путями sb., — а шифрования VLESS в ссылке нет.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?security=tls&flow=xtls-rprx-vision&type=ws`<br>Сообщение: `is not supported over the ws transport`<br>Vision работает на самом соединении TLS. По стенду с Xray: через ws, grpc, http соединения рвёт sing-box, через httpupgrade отказывает Xray, через xhttp Xray берёт flow только с шифрованием VLESS. |
| `flow`<br>`security`<br>`sb.flow`<br>`sb.tls.enabled` | — | **Отказ.** flow-no-tls: flow задан, а TLS, REALITY и шифрования VLESS нет.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?flow=xtls-rprx-vision`<br>Сообщение: `needs TLS or REALITY`<br>Vision работает на соединении TLS или на слое шифрования VLESS: без них его нет. |
| `fm` | — | **Отказ.** finalmask: в fm названа маска, которую sing-box не умеет. У vless, trojan и vmess — любая, кроме fragment и noise; у hysteria2 — любая в списке udp, кроме salamander и noise.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?security=tls&fm=%7B%22udp%22%3A%5B%7B%22type%22%3A%22salamander%22%7D%5D%7D`<br>Сообщение: `fm (finalmask) asks for the mask`<br>Такая маска меняет то, что идёт по сети, и сервер её ждёт. fragment и noise — дело клиента, они дают только предупреждение. |
| `headerType`<br>`security` | — | **Отказ.** tcp-http-header-tls: headerType=http у транспорта tcp вместе с TLS или REALITY.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?security=tls&type=tcp&headerType=http`<br>Сообщение: `is not supported together with TLS`<br>По стенду с Xray: без TLS этот заголовок равен транспорту http sing-box; с TLS тот говорит на HTTP/2. |
| `headerType` | — | **Отказ.** tcp-header: headerType у транспорта tcp, кроме none и http.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?type=tcp&headerType=srtp`<br>Сообщение: `unsupported header type of the TCP transport`<br>Других заголовков у TCP-транспорта нет и в самом Xray. |
| `mode` | — | **Отказ.** grpc-mode: mode у транспорта grpc, кроме gun и multi.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?type=grpc&mode=other`<br>Сообщение: `unsupported gRPC mode`<br>Других режимов нет и в Xray. Режим multi принимается с предупреждением и работает как gun. |
| `serviceName`<br>`mode` | — | **Отказ.** grpc-custom-path: serviceName начинается с «/» (свой путь) и не имеет вида /имя/Tun — несколько частей, другое имя потока или режим multi.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?type=grpc&serviceName=%2Fa%2Fb%2FTun`<br>Сообщение: `supported only as /name/Tun`<br>По стенду с Xray: sing-box строит путь gRPC как /<имя>/Tun и до другого пути не достучится. |
| `quicSecurity` | — | **Отказ.** quic-security: quicSecurity у транспорта quic, кроме none.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?type=quic&quicSecurity=aes-128-gcm&key=k`<br>Сообщение: `the encryption of the QUIC transport`<br>Шифрования пакетов транспорта QUIC из V2Ray в sing-box нет. |
| `headerType` | — | **Отказ.** quic-header: headerType у транспорта quic, кроме none.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?type=quic&headerType=wechat-video`<br>Сообщение: `the packet header of the QUIC transport`<br>Заголовков пакетов транспорта QUIC из V2Ray в sing-box нет. |
| `type` | — | **Отказ.** kcp: type=kcp или type=mkcp.<br>Пример: `vless://6f1c9a0e-3b52-4c1e-9a55-2d4a1b0f7c11@example.org:443?type=kcp`<br>Сообщение: `the mKCP transport is not supported`<br>Транспорта mKCP в sing-box нет. |
| `type`<br>`security`<br>`headerType` | — | **Отказ.** shadowsocks-transport: у ссылки ss транспорт, кроме tcp и raw, security, кроме none, или headerType, кроме none.<br>Пример: `ss://YWVzLTI1Ni1nY206c2VjcmV0@example.org:8388?type=ws&path=%2Fws`<br>Сообщение: `Shadowsocks over the transport`<br>Xray умеет Shadowsocks поверх своих транспортов, TLS и заголовков, sing-box — только в чистом виде. У security и headerType свои тексты: «Shadowsocks over TLS…», «Shadowsocks with a header of the TCP transport…». |
| `<port>`<br>`<path>` | — | **Отказ.** http-not-a-proxy: адрес http:// или https:// без порта («an http address without a port…») или с путём длиннее «/» («an http address with a path…»).<br>Пример: `https://example.org/sub/TOKEN`<br>Сообщение: `is read as the address of a page, not of a proxy`<br>Это адрес страницы или подписки: как прокси он отправил бы трафик веб-серверу. |
| `protocol` | — | **Отказ.** hysteria-protocol: protocol, кроме udp.<br>Пример: `hysteria://example.org:443?protocol=faketcp`<br>Сообщение: `is not supported, only udp`<br>Режимов faketcp и wechat-video первой Hysteria в sing-box нет. |
| `obfs` | — | **Отказ.** hysteria-obfs: obfs, кроме xplus и none.<br>Пример: `hysteria://example.org:443?obfs=salamander`<br>Сообщение: `is not supported, only xplus`<br>У первой Hysteria одна обфускация — xplus; salamander — обфускация Hysteria 2. |
| `<password>` | — | **Отказ.** tuic-v4: в части до @ нет двоеточия и пароля.<br>Пример: `tuic://token@example.org:443`<br>Сообщение: `is of TUIC v4, which is not supported`<br>В TUIC v4 на этом месте стоял токен; sing-box говорит только на v5, с UUID и паролем. |
| `tls_spoof`<br>`sb.tls.spoof`<br>`tfo`<br>`tcp-fast-open`<br>`tcp_fast_open`<br>`sb.tcp_fast_open` | — | **Отказ.** spoof-fast-open: в готовом outbound одновременно есть tls.spoof и tcp_fast_open: true.<br>Пример: `trojan://secret@example.org:443?sni=cdn.example.org&tls_spoof=www.example.org&tfo=1`<br>Сообщение: `tls.spoof does not work with tcp_fast_open`<br>Поддельное приветствие шлётся в установленное соединение, а с TCP Fast Open его устанавливает отправка настоящего: каждое соединение оборвётся. |
| `sb.<path>` | — | **Отказ.** sb-denied: путь называет опцию, которую ссылке задавать нельзя (см. раздел «denied»).<br>Пример: `trojan://secret@example.org:443?sb.detour=direct`<br>Сообщение: `is not for a link to set`<br>Ссылка настраивает только то, как достучаться до своего сервера. |
| `sb.<path>` | — | **Отказ.** sb-unknown: опции с таким путём у этого outbound в этой сборке sing-box нет; сюда же — пустая часть пути (sb.tls..fragment, «names no option»).<br>Пример: `trojan://secret@example.org:443?sb.no_such_option=1`<br>Сообщение: `this sing-box has no option no_such_option`<br>Набор опций зависит от линии sing-box: то, что есть в 1.14, может отсутствовать в 1.13. |
| `sb.<path>` | — | **Отказ.** sb-value: значение не читается как тип, который имеет опция.<br>Пример: `trojan://secret@example.org:443?sb.tls.fragment=maybe`<br>Сообщение: `does not fit the option`<br>Не 1/0 у флага, не число у числа, длительность без единицы. Так же отвергается негодное значение у имени другого клиента (tfo=yes). |
